# Specification: USB3 Vision Camera

**Track ID:** usb3-vision-camera_20261021
**Type:** Feature
**Created:** 2026-10-21
**Status:** Complete

## Summary

Add a generic USB3 Vision `FrameCamera` driver for Linux and macOS first, then Windows. It uses a GenICam core taken out of the Spinnaker driver, with an Aravis backend (Linux/macOS, primary) and a GenTL backend (Windows, secondary). The first camera is the IDS U3-36P0XCP-M-GL.

## Context

The Spinnaker driver only works with FLIR cameras and only on Python 3.12. Most of its logic is GenICam SFNC behaviour that any USB3 Vision camera shares: settings and units, pausing acquisition for some writes, software triggering, the timestamp offset, and the `not_before` stale-frame loop.

No single Python stack covers all three OSes:

- **Aravis** (open source, libusb, via PyGObject) works on Linux and macOS without a manufacturer SDK. It needs only Aravis, PyGObject, and a udev rule on Linux. On Windows it would probably need the camera rebound to WinUSB, which displaces the vendor driver.
- **GenTL** (`genicam` / Harvesters plus a vendor `.cti` producer) works on Windows and Linux. It needs a vendor SDK such as IDS peak, which supplies the producer and, on Windows, the USB driver. No macOS U3V producer was found. `genicam` 1.6.0 ships wheels for cp310–cp314 on all three OSes. Harvesters' last release was 1.4.3 (May 2024).

Linux and macOS are the priority platforms, and Windows comes second.

The IDS U3-36P0XCP-M-GL (uEye XCP) is USB3 Vision and GenICam compliant, according to distributor listings. It has a 20 MP monochrome onsemi AR2020 sensor with a rolling shutter.

## User Story

As a lab developer, I want any USB3 Vision camera behind the `FrameCamera` interface on whichever OS the rig runs, so that adding a camera brand doesn't mean writing a new driver.

## Acceptance Criteria

- [x] The SFNC logic lives in one shared GenICam core. The Spinnaker driver is rebuilt on it with no change callers can see: its existing unit and contract tests pass unmodified, and its hardware tests pass on the CM3-U3-50S5M.
- [x] An Aravis backend drives the IDS camera on macOS and Linux. Neither OS needs a manufacturer SDK, only Aravis, PyGObject, and a udev rule on Linux.
- [x] A GenTL backend drives the IDS camera on Windows through the IDS peak producer, and is also tested on Linux as an alternative to Aravis. If no Windows machine is available, the backend ships tested against fakes and the Windows hardware check is recorded as outstanding.
- [x] Optional features (software trigger, throughput limit, timestamp latch, auto modes) are probed at `open()`. Settings for features the camera lacks are left out rather than failing.
- [x] Vendor libraries are imported lazily. A missing one raises `ImportError` that points to the install steps for each OS.
- [x] Both new backends pass the `Camera`/`FrameCamera` contract suites against fakes in CI.
- [x] `el-devices` gets a subcommand for the generic driver. Hardware docs cover installing on each OS and record what was learned about the IDS camera.
- [x] An ADR records the shared-core/backend design.

## Dependencies

- spinnaker-camera_20261012. Its driver and tests are the source and the regression net.
- No changes to the `Camera` ABC are expected. Any change needs maintainer approval under the workflow rules.

## Out of Scope

- GigE Vision. Both backends support it, but it won't be tested or documented here.
- Hardware triggering, chunk data, events, image geometry (ROI, binning), and packed pixel formats. This matches what the Spinnaker driver leaves out.
- Removing or deprecating the Spinnaker driver.
- Aravis on Windows. GenTL is the Windows path.
