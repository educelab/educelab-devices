# Specification: gphoto2 Single-Setting Reads

**Track ID:** gphoto2-single-setting_20261102
**Type:** Bug
**Created:** 2026-11-02
**Status:** Draft

## Summary

`setting()` and `set_setting()` on a `GPhoto2Camera` read the whole config tree, which takes 2.6–2.8 s on the Z7 II. They should read only the widget they need. Reported from PGS Spectral (pgs-scan, branch `spectral-app`, MR !61).

## Context

Device APIs are blocking, and the camera lock is held for the whole call (ADR 0001). A slow `set_setting` therefore stalls the preview and every other call on that camera. The write itself is already cheap: `Session.set_config` writes one widget through `get_single_config`/`set_single_config`.

## Problem Description

- `Camera.set_setting` (`cameras/base.py:162`) validates against `self._setting(name)`.
- The default `_setting` (`base.py:172`) is `self._settings()[name]`.
- `GPhoto2Camera._settings()` (`gphoto2.py:364`) calls `session.config()`, which walks and flattens the whole tree.
- `Camera.setting(name)` takes the same path.

Each exposure-and-ISO change is two `set_setting` calls, about 5.4 s with the lock held. A 16-band dataset spends 40–85 s in these validation reads alone. This was found by reading the code, and hasn't been measured on the body yet.

## Acceptance Criteria

- [ ] Once the name-to-widget mapping exists, `setting()` and `set_setting()` make no whole-tree reads. A fake-`Session` test counts `config()` calls.
- [ ] Each call still reads its setting fresh, so validation sees current choices (e.g. shutter speeds after a mode change). This keeps the guide's snapshot rule. A `Setting` is never cached.
- [ ] A setting read from one widget equals the one `settings()` returns for that name, for both canonical and native settings.
- [ ] On a camera driver without single-widget access (`-6`), or for a name the mapping doesn't hold, both calls still work through the whole tree. A name the camera doesn't have still raises `KeyError`.
- [ ] The Z7 II single-widget read time is measured and recorded in `docs/hardware/gphoto2-cameras.md`. The **Writes** bullet is corrected to state what `set_setting` costs.
- [ ] `tests/test_gphoto2_hardware.py` passes on the Z7 II.

## Dependencies

- Existing code: `cameras/gphoto2.py` (`_settings`, `_writers`, `_Canonical`, `_native_setting`), `cameras/_gphoto2.py` (`Session.config`, `Session.value`, `flatten_config`), `tests/fakes/gphoto2.py` and `tests/test_gphoto2.py`.
- Hardware: the Z7 II on the lab Mac rig. The rig is shared, so book time before running hardware tests.
- Independent of `preview-mode_20261102`.

## Out of Scope

- Making `settings()` faster. It stays one full read by design. Callers that need several settings can take one snapshot.
- Validating against a cached `Setting`. That would break the snapshot rule.
- Multi-widget writes (e.g. turning live view on), which still do one whole-tree round trip.
- Changes in pgs-scan.

## Technical Notes

- Each canonical setting resolves to a single widget (the first of `_Canonical.widgets` the camera has), so a fresh read of one setting is always a single-widget read.
- `flatten_config` sets `Widget.section`, which `_settings()` uses to skip `actions`. A single-widget read can't see the section, but the mapping is built from a full read and already excludes those widgets.
- If a mapped widget disappears (`get_single_config` gives bad parameters), fall back to a full read and rebuild the mapping.
- Per the handoff, the mapping can be built at `open()` or on first use. Both cost one full read.
